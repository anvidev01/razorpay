# 07 — Agent-Aware Risk: Honest Metrics  [Track 02]

> **The bar:** *"Build a working detector, verifier or auto-responder for one class of
> loss, with measured precision and recall on a held-out test set. Honest metrics
> including false-positive cost. Strictly defense-only."*

Reproduce: `./build/rig-riskeval [seed] [sessions]` — default `42 400`.
The full labelled set is written to `wal/riskeval_dataset.csv` for inspection.

---

## 1. Method

**The class of loss:** an agent transacting outside its owner's normal pattern —
a hijacked or looping agent draining a mandate, exfiltrating to an unknown merchant,
or operating at hours its owner never does.

**Data.** There is no public corpus of labelled agentic-payment fraud; the rails are
months old. So the dataset is generated by a **documented, seeded behaviour model**
(`engine/src/dataset.cpp`) whose assumptions can be argued with — which is more honest
than hand-picked examples that flatter the detector. Seed 42 reproduces byte-identically
on any machine.

It deliberately contains **hard negatives** — legitimate-but-unusual traffic (a late
lunch, a double-size team order, an occasional different merchant). Without those the
normal class is trivially separable and the false-positive rate is fiction.

**Split.** Sessions are divided ~60/40 by a hash of the session id. A session's entire
history lands on one side: splitting mid-session would leak the answer, because the
detector scores each transaction *against that session's own history*.

**Tuning.** 192 threshold combinations swept on **train only**, selecting the highest
recall subject to a false-positive rate ≤ 2%. Reported headline numbers come from
**test**, which tuning never saw. Train numbers are printed beside them so overfitting
is visible rather than assumed away.

## 2. Results (seed 42, 400 sessions, 8,719 transactions)

```
                TP     FP     TN     FN   precision  recall    FPR
  train         66      8   4763    189      0.892   0.259   0.002   (tuned on this)
  TEST          69      7   3457    160      0.908   0.301   0.002   held out
  F1 train 0.401 vs test 0.452  (gap -0.051 — no meaningful overfitting)
```

| metric (held-out) | value |
|---|---:|
| precision | **0.908** |
| recall | **0.301** |
| false-positive rate | **0.002** |
| legitimate traffic prompted | **0.20%** |

## 3. The tradeoff, not one flattering point

A single operating point is a claim; the curve is the honest picture, and it lets a
merchant choose their own friction budget:

| score threshold | precision | recall | FPR | good traffic prompted |
|---|---:|---:|---:|---:|
| 1 | 0.379 | 0.803 | 0.087 | 8.69% |
| 2 | 0.526 | 0.524 | 0.031 | 3.12% |
| **3 (chosen)** | **0.908** | **0.301** | **0.002** | **0.20%** |

Recall 0.80 is available at threshold 1. It costs 8.7% of good traffic a confirmation
prompt. That is the trade being made, stated plainly.

## 4. False-positive cost

**A flag is `REVIEW`, never `DENY`.** The customer gets one confirmation prompt and the
purchase completes. Nothing is declined, so the *revenue* cost of a false positive is
**zero**; the cost is friction, bounded at **0.20% of legitimate transactions**.

That is the entire reason the engine has three outcomes instead of two. Auto-blocking on
a probabilistic score converts every false positive into a lost sale.

## 5. Recall 0.30 is the honest number, and here is why it is acceptable

This detector is the **last** line, not the first. Every one of the 160 missed anomalies
is still bounded by the deterministic controls it sits behind: mandate budget, per-item
price cap, aggregate quantity cap, merchant allowlist, mandate TTL. A missed anomaly is
a purchase whose *shape* the human already authorised — it is not a free hand.

Chasing recall here would spend real customers' patience re-detecting what the kernel
already refuses deterministically.

## 6. What the held-out set caught in my own detector

The first version of this evaluation used **24 hand-written cases that I had also tuned
the thresholds against**, and reported *precision 1.00, recall 0.62, FPR 0.00*.

On a proper held-out set that same detector scored **precision 0.278, FPR 12.1%**.

The cause was a design error, not a tuning one: the detector fired on **any single
signal**, and `R_NEW_MERCHANT` alone is not evidence — **906 legitimate transactions**
in the set were at a merchant the agent had not used before. Ordinary merchant
diversity was being reported as compromise.

Fixed by weighting: burst 3, sustained velocity 2, new merchant 1, odd hour 1, flag at
≥ 3. A weak signal must now corroborate rather than accuse, and a never-seen merchant
only counts once the agent has an established narrow pattern (≥ 8 transactions across
≤ 3 merchants). Precision went 0.278 → 0.908 and FPR 12.1% → 0.2%.

**Two harness bugs surfaced with it**, both of which would have produced misleading
numbers: when no threshold combination met the FPR budget the sweep silently reported
*untuned defaults* as if they had been chosen, and a `printf` format mismatch was
reading a pointer as a double and segfaulting. The build had no warning flags; it does
now (`-Wall -Wextra -Wformat=2`).

## 7. Strictly defense-only

- Output is **one bit**: ask the human, or do not. No blocking, no account action, no
  automated punitive step of any kind.
- **No profiling of the person.** The baseline is per agent *session*: merchant ids,
  hour-of-day, transaction count, amount. No PII, no device fingerprinting, no
  cross-user data, nothing transmitted anywhere.
- Every signal that fired is written to the audit log, so a reviewer can see exactly
  why a step-up was requested — including signals that were observed but did not reach
  the threshold.
- Nothing here is offense-capable: there is no probing, no evasion, no capability that
  works against a third party.

## 8. Replayability caveat

Behavioural bits derive from cross-transaction state, so a single-record replay cannot
re-derive them. Both auditors exclude `STATEFUL_RISK_MASK` from the reproducibility
check and report how many decisions carried such bits. The deterministic kernel stays
100% replayable by two independent implementations; the risk layer is recorded and
explainable, but honestly labelled as not reproducible from one record alone.

## Future work

Per-merchant-category baselines; sequence models over agent action traces (thresholds
only today); feeding confirmed step-up outcomes back as labels; and evaluation against
real traffic once agentic volume exists to learn from.

# Appendix — Revenue impact  [Track 01]

> Track 01's headline is *"Grow the merchant's revenue."* Every other metric in this
> project is defensive. This one answers what the gateway **earns**.

Reproduce: `./build/rig-revenue [seed] [sessions]`

## Method

The same seeded, held-out data the detector is evaluated on, run through four policies so
the comparison is like-for-like:

| | policy |
|---|---|
| **A** | limit-only — what the rail does today: approve anything under the block |
| **B** | naive blocker — deterministic caps, and any risk signal **denies** |
| **B+** | the same design tuned for catch rate (0.80 recall) — what a risk owner actually ships |
| **C** | this gateway — caps deny, risk signals **escalate** |

Two quantities are separated deliberately, because lumping them hides the only number the
policies differ on:

- **outside the mandate** — legitimate, but the human never authorised it. Refusing this
  is the product working; it is not lost revenue.
- **sales killed** — legitimate, *inside* the mandate, refused anyway. This is a real loss.

## Result (seed 42, 400 sessions, held-out split)

```
policy                      fraud thru   sales killed   revenue kept   prompts
A · limit-only                 143,059              0      1,360,230         0
B · naive blocker               47,201          1,054      1,319,206         0
B+ · naive, tuned to catch      18,104         79,542      1,240,718         0
C · intent gateway              47,201              0      1,320,260        61
```

| | |
|---|---:|
| fraud prevented vs the rail today | **+₹95,858** |
| revenue preserved vs a blocker at 0.80 recall | **+₹79,542** (+6.4%) |
| sales this gateway killed | **₹0** |
| friction | 61 confirmations across 3,693 purchases (1.7%) |

## The argument, netted out honestly

The aggressive blocker **does** prevent ₹29,097 more fraud than this gateway. It spends
**₹79,542 of real sales** to do it.

**Net position: the gateway is ₹50,445 ahead for the merchant** — not because it detects
better, but because an uncertain signal becomes a question instead of a decline.

That is the entire commercial case for `REVIEW` as a third outcome, and it is why the
detector's honest 0.30 recall is not the weakness it looks like.

## Assumptions, stated rather than buried

- **The traffic is synthetic.** No public corpus of agentic-payment fraud exists — the
  rails are months old. These are the consequences of a documented behaviour model
  (`engine/src/dataset.cpp`), not a measurement of real revenue. Argue with the model.
- **A step-up prompt is answered correctly**: people approve their own purchases and
  decline ones they did not make. The whole comparison rests on this, so it is stated.
- **Mandate modelled** as ₹1,200 per purchase, merchants 1–6.
