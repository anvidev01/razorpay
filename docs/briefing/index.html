Mandate Engine

UPI Reserve Pay lets an AI agent spend your money. The rail enforces exactly one thing — is the agent under its limit. It never looks at the cart. So an agent told “order lunch under ₹500” can buy a ₹6,000 blender, and the payment succeeds.

The gateway asks the question the rail doesn’t: does this cart match what the human actually agreed to? A branch-free C++ kernel answers it in 28 nanoseconds, and no payment token can exist until that answer is durable in a hash-chained log.

03

Explainable, by construction

The kernel evaluates every rule and accumulates into a bitfield — it never short-circuits. A bad cart reports all its reasons, not the first one.

cart: SKU_APPLIANCE_BLENDER_5 added to a lunch mandate verdict 0x000D · eval 31 ns
1u << 0 R_SKU_NOT_IN_INTENT appliance is not in {MEAL, DRINK, SIDE}
1u << 2 R_UNIT_PRICE_EXCEEDED ₹6,000 exceeds the ₹500 per-item cap
1u << 3 R_CART_TOTAL_EXCEEDED ₹6,420 exceeds the ₹500 mandate budget

Graceful failure is the product

Blocking is easy; blocking without breaking the user is the point. The denial carries repair hints — the agent drops the blender, resubmits, and the lunch still arrives. Then the user gets one tap to approve the blender deliberately with MFA, which mints a new mandate and the same engine allows it. It degrades to ask the human, never to fail the task and never to allow it anyway.

Replay is the proof

Because evaluate() is pure — no allocation, no clock read, no floating point — every historical decision can be re-executed offline and checked against what was logged.

04

Decisions the measurements forced

Three architectural calls that came out of benchmarking, two of which reversed my starting instinct.

QuestionWhat the measurement saidΔCall
Hand-rolled parser or simdjson? Hand-rolled won p50 by 7%, lost p99 by 12% 282 vs 248 ns simdjson
Verify the signature per cart? Ed25519 is 1,302× the kernel — it would dominate everything 36,458 ns verify once at admission
Is fsync() enough for the WAL? On macOS it does not flush the drive cache — the guarantee would be fiction 3.96 ms F_FULLFSYNC + group commit
Pad everything to the 128 B line? 64 B captures 98% of the win; 128 B adds 6% and halves L1 density 5.9× → 6% 64 B, except 2 fields
Vectorise the kernel with NEON? Would optimise 13% of the decision; search domain is already one cache line 28 ns stay scalar
05

What broke at 2 AM

SIGSEGV at 41,000 rps, never under the debugger, and some survivors wrote corrupt POLICY_DECISION records — the one artefact whose integrity is the whole premise. Reproduced and committed as a test.

The trap

A pool allocator makes your program invisible to ASan

simdjson returns string_views into its own buffer. The audit ring retained them across a request boundary, then the arena reset underneath. But ASan only tracks malloc: the arena mallocs one 4 MB slab at startup, so every byte stays “live” forever. A use-after-free inside a pool is an ordinary read of valid memory.

The fix — to the tooling, first

Three lines, then a 9-second repro

void reset(){
  ASAN_POISON_MEMORY_REGION(base, head);
  head = 0;
}

Same bug, same logic, only the instrumentation differs:

POISON=0  exit 0, silent      ← the trap
POISON=1  use-after-poison    ← caught
After interning SKUs to uint32 at the parse boundaryBeforeAfter

▲ The fix made it 2.6× faster — the hot loop stopped comparing strings. p99 improved 5.8× because string compares are data-dependent, producing exactly the tail the branch-free design was meant to eliminate.
